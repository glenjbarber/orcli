# 0000003 The first request is the connection test

- Status: accepted, and SUPERCEDED by `UI-redesign.md`, which supersedes every prior UI architecture ADR
- Date: 2026-10-05
- Supersedes: a command in the table that tested the connection and reported the
  key, with no handler behind it

## Context

The command table listed a connection command that no handler implemented. A
listed command with no body is one a reader types and is told this build does not
run it, which reads worse than a name that is not there at all.

There was also a real question behind it: when is the endpoint believed to work,
and when is a preference written to the configuration file that the endpoint has
not yet agreed to.

## Decision

There is no connection command. The connection is automatic and the probe is the
reader's own first request.

A request that completed having delivered text has proved the credential and the
model together, and that is what writes the model to the configuration file. A
request that delivered nothing writes nothing, and this holds even when the
endpoint reported the request as complete: a cut stream has proved nothing, and a
preference written on that evidence is one nobody has reached the endpoint with.

The write happens once per session. The first request is the probe, and every
request after that writing the same preference again is a write nobody asked for.

A failed write is reported to the reader rather than raised. The request was
answered and the answer is the thing that was asked for, so a preference that
could not be written is an inconvenience rather than a lost reply.

## Consequences

There is nothing to keep in step with, since a separate check and a real request
would both have to know when the endpoint works.

The first request a reader asks doubles as the probe, so the reader sees no row
they did not type. There is no way to prove the connection without spending a
request, which is the point.

A model is written only on evidence. A reader who named a model the endpoint does
not offer finds out from the refusal on their first request rather than before
it, since nothing here consults a catalogue. A request that fails writes nothing,
so the file is left as the reader last had it.

The confirmation is wired from outside the interface, since the writer belongs to
the caller and the interface holds no configuration.

## Alternatives considered

A command calling a catalogue endpoint and checking the model against what came
back. It proves the key and the model in one request, and it needs a catalogue
fetch the transport does not have, so a second method and a second parse would
exist to be kept working. A credential that authenticates but is not entitled to
the catalogue would then be unable to write anything at all.

A dedicated probe request carrying a fixed short prompt. It is one request either
way, and it puts a row on the reader's screen that they did not type.

Waiting for a second request to confirm. It proves the same thing more slowly and
leaves the first reply unwritten, which is the outcome a reader would rather not
meet.

## Notes

The preference that gets written is the model, and it is written without
recording the model it replaced. A first request is a probe rather than a move,
and treating it as one would send a reader back to a model they never chose. See
0000004.
